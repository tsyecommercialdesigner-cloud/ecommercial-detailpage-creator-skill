# Agent Skills 工程与 CI/CD 规范

本指南供实际 Skills 开发项目采用，维护设计、实现、验证、CI/CD 和 Git 跟踪要求；安装与使用文档见[手册与交付指南](MANUAL-WRITING-GUIDE.md)。开放格式、宿主实现与项目工程选择分别记录。这里规定消费项目应落实的能力，不表示模板维护仓库已经实现或验证这些能力。

按改动选择章节：需求与作用域见第 1 节，正文与资源见第 2 节，脚本和依赖见第 3 节，工具与权限见第 4 节，验证见第 5 节，流水线和发布见第 6 节，忽略规则见第 7 节。跨范围变更读取所有受影响章节。

## 1. 需求与项目约定

- 先核对任务目标、当前需求、验收条件和现有实现，说明目标用户、输入、预期产物、非目标及失败条件。实现与需求有差异时记录差异，不改写需求掩盖缺陷。
- 采用 spec-kit 时读取实际项目的 constitution、当前功能的 spec、plan、tasks 及 contracts；常见位置是 `.specify/memory/constitution.md` 与 `specs/<feature>/`，以实际版本为准。需求、技术决策和执行状态各有来源，沿用既有任务系统；不因套用规范自动初始化工具。
- 项目 README 或开发文档提供真实目录地图、技能入口、相关检查命令和适用边界。新项目只记录已确定事实；遗留项目补充已知限制，协作项目按需补充负责人和交接规则。
- AGENTS.md 及变体只保留核心约定和带场景的相对链接。细则单一维护；仅在局部约束改变执行方式时增加目录级入口，按目标宿主核对发现、继承与冲突行为。局部文件不能自行取消更高层约束。
- 纯指令、脚本型、外部工具型分别设计。按真实瓶颈增加脚本、MCP、子 Agent 或编排能力；不为补齐模板而引入无关组件。
- Skill 围绕业务结果组织方法与标准；MCP Server 提供契约明确的外部能力，Agent 在 Host 中加载指令、选择并调用工具。权限、隔离及业务不变量由宿主、执行环境与服务端落实；Skill 不替代服务端校验，MCP 不自带沙箱，也不是唯一执行途径。

### 1.1 适用边界与复用价值

- 新建 Skill 前先检索已有技能与共享方法，判断能否直接复用、补充资源或改进现有技能。优先沉淀重复发生、有团队共享价值且能持续验证的方法；一次性需求通常直接用提示或已有工具处理，不为完成一次任务创建整套技能工程。
- 在需求或设计记录中简述预期使用频率、单次收益、共享范围和开发／维护／评测成本，统一时间或成本口径后比较，不套用未经核实的收益数字。低频不等于无价值，高风险任务的质量及风险收益也需考虑；不强设统一频次或 ROI 门槛。

| 判断维度 | 设计前须明确的内容 |
|---|---|
| 目标 | 输入与使用者需求是否明确，成功及失败能否用契约、证据或质量量规判断；不要求所有目标都用单一数值衡量。 |
| 路径 | 是否已有可复用方法、前提与分支；只固定必要约束，明确哪些环节需探索或人工判断，不要求全部任务只有唯一流程。 |
| 结果 | 能否定义产物、质量标准与不可接受结果；允许多个合格答案，但不能以“任何结果都算成功”替代验收。 |

- 目标、方法或判据尚不清楚时先澄清或试验，将假设与已验证结论分开。探索任务可复用检索、记录、验证等稳定子流程，不把未经验证的假说或试错路线固化为强制 SOP；方法成熟后再决定是否抽取、合并或新建 Skill。实验草案可在分支中编写和验证，明确其状态，不将未验证草案作为团队稳定版本发布。
- 使用后对照实际复用、效果和维护负担复评；重叠技能优先合并或明确分工，失效规则及时修订／弃用并说明替代路径，不以技能数量作为知识沉淀成果。

### 1.2 Git 协作与知识回流

团队约定的共享 Git 技能库维护可追溯的知识基线。协作循环为：共享版本使用 → 发现问题／提出改进 → 分支修改并补充回归样例 → PR 与维护者评审、必需 CI → 合并后复验 → 受控发布与团队分发 → 使用反馈再次回流。CI、发布及权限细则按第 6 节执行。

- 贡献入口面向有权限的团队成员，维护者负责专业适用性与质量把关，不垄断知识贡献。复用已有 PR 模板、评审规则与任务系统；按项目实际分工记录维护者，不照搬特定岗位名称或强制设立额外组织层级。
- 方法改进、缺陷修复与功能扩展在共享基线上发起 PR，关联问题、适用边界、变更原因、代表性输入输出与验证结果。正文、引用资源、脚本、必要依赖及回归样例同步变更；资料先脱敏并核对许可，不将用户私有数据或完整会话直接作为知识资产提交。
- 维护者评审正确性、复用范围、近邻技能冲突、兼容性及风险，CI 验证可自动化的质量基线；模型行为评测按第 5–6 节提供相应证据，未自动验证项明确记录，不用仅格式通过代替有效性。变更后的提交按项目规则重新检查和评审。
- 合入后的已验证版本通过受控 CD 发布到团队约定渠道，关联版本／提交、变更记录、兼容范围及更新／回滚办法。消费端核对已安装版本，按既有授权和更新策略同步；发布不等于所有成员已更新，不擅自覆盖本地定制或强制升级。
- 本地实验和必要定制可在分支进行；可共享改进经验证后回流，不以长期未同步的个人副本代替共享维护。确需保留分支或变体时记录用途、责任、上游基线及同步方式；共用知识单一维护，产物引用与版本固化按第 2.4 节执行，避免复制后漂移。
- 使用反馈关联实际版本、场景、失败样例与验收证据，进入现有 issue／PR 流程，形成团队成员可持续贡献、复用和改进的知识网络。知识归档不自行授予提交、推送、通知或发布权限。

### 1.3 MVP 先行与扩展门槛

- **先做闭环**：新建 Skills 开发项目先选一个真实任务，明确输入、输出和成功／失败条件，再交付最小可运行 Skill。纯指令任务可仅含带 YAML 元数据与正文的 `SKILL.md`；确需脚本或外部工具时只实现该闭环的必需部分，不用占位成功或虚构结果冒充 MVP。
- **先验选择**：优先验证 `description` 是否同时说清“做什么”和“何时用”。在首要目标 Host 中检查元数据解析、技能发现、显式调用、自然语言正例与近邻反例，再验证代表性输入到输出及失败反馈；仅显式调用的技能须验证预期不自动触发。不得跳过声明的调用策略检查，不能只证明文件存在。
- **通过再扩展**：将目标版本、场景及检查结果关联现有任务；MVP 未通过，不得叠加额外功能、依赖、编排或批量宿主适配。缺环境或权限时记录阻塞，不把未验证当通过；先修复基础缺陷，再逐项扩展并回归最小闭环。新增 Host 分别验收，不将首个 Host 通过推断为全部兼容。
- **保留基线**：将 MVP 场景保留为回归依据，确定性检查接入 CI，行为证据按第 5–6 节维护；后续能力须有需求依据。已有项目先复验可运行最小基线再增量修改，不为执行本流程重建仓库、删除历史或降低既有验收标准。

## 2. SKILL.md 与资源设计

每个 Skill 聚焦一类可复用任务。按[开放格式规范](https://agentskills.io/specification)维护 `SKILL.md`；核对依据版本或日期，并区分格式要求与下列工程要求。

| 项目 | 要求 |
|---|---|
| 入口 | 每个 Skill 独占一个目录，根部只有一个大小写准确的 `SKILL.md`；顶部 YAML frontmatter，随后为 Markdown 正文。资源按第 2.1 节组织。 |
| `name` | 必填字符串，1–64 字符，与技能目录名完全一致；匹配 `^[a-z0-9]+(?:-[a-z0-9]+)*$`，不含空格、大写、下划线或标签，另检查目标宿主保留名。 |
| `description` | 必填纯文本字符串，1–1024 字符，不含 XML 标签；必须同时明确功能定义和触发场景，前置关键用途与近邻边界，不以泛称或正文链接代替选择线索。 |
| 可选字段 | 按需使用 `license`、`compatibility`、`metadata`；`compatibility` 提供时为 1–500 字符，`metadata` 为字符串键值映射。自定义信息优先放 `metadata`。 |
| 产品扩展 | `allowed-tools` 是实验字段，其语义由宿主实现；其他产品字段和 `agents/openai.yaml` 等适配文件分别核对，不作为通用必需项。 |

正文按五个维度审阅，标题可按任务组织，不要求机械复制五个章节：

| 维度 | 必须讲清的内容 |
|---|---|
| 定时机 | 适用请求、必要前提、不适用场景及相邻技能消歧；与 `description` 一致。 |
| 立目标 | 明确的任务结果、输出对象与完成标准，不夸大能力。 |
| 理规则 | 必需输入及缺失处理，关键顺序、判断分支、资源／工具、输出约定和结果核验。固定必要约束，保留任务需要的合理执行路径。 |
| 给示例 | 代表性的正确输入输出、反例／不适用情形、失败反馈；与真实能力一致。大量样例另存，便于引用和评测。 |
| 划边界 | 处理范围、权限与副作用、无法完成时的反馈、可重试条件及需要人工判断的条件。 |

- 入口保留关键决策、边界及验证要求，详细知识按第 2.1 节拆分并直接引用。渐进式披露以实际按需读取为准，不能仅将整篇内容搬进另一个大文件或无条件一次加载所有资源；建议篇幅不作为格式或行为通过依据。
- 所有必需引用目标应可从发行版本取得；检查缺失、越界及符号链接／重解析点逃逸。第三方代码、资料和 assets 核对来源与许可，不将私有业务数据混入示例。
- 组合技能时说明输入输出、状态传递和部分失败责任。需要机器消费时定义相应契约；不要声称开放格式自带统一函数 API、JSON Schema 或错误码。
- 按任务组织 Skill，不把一个 Server 的全部工具目录直接变成技能正文。各步骤明确必需输入、前置条件、产物、成功判据及失败分支；区分计划、草稿、已执行和已核验结果，不以调用成功代替任务完成。
- 稳定业务方法与宿主适配分别维护。入口保留目标、关键决策及边界；兼容差异、工具映射、参数模板和大量样例按触发条件引用。接口 schema 引用实际服务的权威契约，模板标明依据版本及需填写字段，避免多份复制后漂移。
- 会影响正确性的固定计算、必须经过的检查或审批用脚本、工作流或服务端约束落实；自然语言 SOP 不能保证步骤必然执行。仅对任务需要的环节采用确定性机制，不强制所有 Skill 脚本化。

### 2.1 产物目录、一级引用与命名

本节约束开发出来的单个 Skill 包及其运行引用，属于本项目工程约定，不是对开放格式新增通用限制。开发项目的仓库、测试／评测、CI、开发文档及技能父目录可沿用既有布局；不要把整个仓库改造成以下结构。

Codex、Claude Code、DeepSeek Harness 的共享产物均采用“一个技能目录 + 一个 `SKILL.md`”；无额外资源时可只交付该文件。安装位置、发现范围和同名裁决分别按[宿主目录约定](MANUAL-WRITING-GUIDE.md#21-skills-存放位置与生效范围)核对，不将 Claude 专属路径、缓存或覆盖顺序作为通用要求；DSH 的扁平 Markdown 等扩展不作为共享包基线。

开放格式允许额外目录，`assets/` 的官方用途包括模板和静态资源；本项目进一步将模板统一分入 `templates/`，保留 `assets/` 存放素材。这是工程分工，不是宿主只识别某个资源目录名的限制；目录存在不能代替入口引用、完整打包及实际可读性验证。

```text
<skill_name>/
├── SKILL.md
├── references/
│   ├── finance-rules.md
│   └── sales-rules.md
├── scripts/
│   └── validate_inputs.py
├── templates/
│   └── report-template.json
└── assets/
    └── logo.png
```

- 根目录放 `SKILL.md`，辅助文档统一放 `references/`（复数），执行脚本放 `scripts/`，模板放 `templates/`，图片、字体等素材放 `assets/`。资源采用一级子目录，目录内平铺有意义的文件，不继续套多层分类；按需建立，不生成无用途的空目录或示例文件。目标宿主要求的 `agents/openai.yaml` 等适配文件按其实际格式保留。
- **扁平引用**：目录深度与引用跳数分别验收；`SKILL.md` 直接指向目标及读取条件，必需指导最多一跳。禁止 `SKILL.md → helper.md → rules.md` 链式加载；辅助文档包含本主题所需说明，其他主题仍由入口直接索引。
- **复杂知识按功能域拆分**：禁止将大量规则、契约、示例及不同领域资料堆在 `SKILL.md` 或单个辅助文档中。按财务、销售等实际功能域在 `references/` 平铺拆分；入口说明各文件用途及触发条件，只读取当前任务需要的内容。用相关任务验证未无条件加载其他领域，节省 token 的同时不遗漏关键规则，不承诺“零 token”。
- **相对路径与正斜杠**：包内资源以技能根为基准使用相对路径和 `/`，大小写一致，不写本机绝对路径或越界引用。脚本显式解析资源基准，区分调用方工作目录、用户输入输出；原生 Windows／WSL／远端分别验证，不假定统一 Linux 环境。
- **命名**：技能目录与 `name` 遵守本节上方的格式约定；入口固定为 `SKILL.md`。资源文件名体现主题或用途，优先小写英文、数字与连字符，脚本遵从所用语言约定；不使用 `doc1.md`、`file2.txt` 等无意义名称，不用大小写差异区分两个资源。保留产品要求的固定文件名与必要后缀，引用和重命名同步更新。
- **验收**：分别核对单 Skill 包的资源子目录、入口一跳引用、功能域拆分、读取条件、命名及文件可达性；运行引用必须随版本交付。迁移旧目录或模板位置时同步调整链接、脚本和包清单并回归，不以批量更名修改用户已安装副本；按既有授权交付更新版本。

### 2.2 元数据写作与选择

元数据须在正文尚未加载时提供能力识别与选择线索；格式边界见上表，实际路由还受 Host 实现影响。

- **YAML**：首行 `---`，成对分隔符后写正文；缩进只用空格，不用 Tab，映射冒号后留空格，特殊字符／多行值正确引用，不重复定义。标准字段保留规定的小写键名；扩展字段按宿主拼写，不批量改大小写。必需字段不外置，流程不塞入 YAML；用实际 YAML 解析器及字段校验检查，Markdown 渲染正常不能代替格式通过。
- **名称**：优先表达动作与对象，使用稳定 kebab-case，不强制某一种动名词词形。避免泛称、随机编号和随版本频繁改名；检查重名与语义重叠。改名同步目录、调用、引用、适配与回归，别名／命名空间按 Host 核对。
- **描述核心要求**：`description` 必须同时写明“功能定义（对象、动作、产物）”与“触发场景（用户意图、输入前提）”，并简述近邻排除；缺任一要素不得通过写作验收。用第三人称或客观陈述前置关键信息，不写泛称、只列精确口令或“详见正文”，不堆砌关键词。
- **内容边界**：只描述真实能力，不写宣传语、长步骤、完整参数表、秘密或大量样例。长度上限不作为写满目标；裁剪后仍应保留关键用途与边界。
- **三宿主兼容**：名称与标准元数据须满足所声明 Codex／Claude Code／DSH 版本的共同约束，并分别核对保留名、扩展字段及调用策略；不把 Claude 保留字当成统一标准。发现、解析与实际选用分别验证；未发现时核对加载范围、宿主诊断及格式校验结果，不以模型自报可用为证。不因一个 Host 通过就宣称其余兼容。
- **扩展信息**：仅按需填写 `compatibility` 等字段；作者、版本放 `metadata` 字符串映射。宿主扩展及 `agents/openai.yaml` 单独核对，与正文一致；不假定任意顶层字段均可用，也不把调用开关当权限授权。

以下仅为写作对照，消费项目须按真实能力改写：

| 项目 | 正例 | 反例及原因 |
|---|---|---|
| 名称 | `pdf-table-extraction`，表达对象与任务。 | `file-helper-v2`，范围含混，日常版本更新容易导致标识漂移。 |
| 描述 | “提取文本型 PDF 的表格并转换为结构化数据；用户需要整理 PDF 表格时使用。不处理扫描图像的 OCR。” | “处理各种文件，使用时详见正文。”缺少任务、触发和边界，未加载正文时无法有效判断。 |

### 2.3 Markdown 正文与渐进式披露

正文是 Skill 被选用后的操作入口，应能指导 Agent 开始执行并判断结果；资源索引是其中一部分，不能把正文退化为只有链接的空目录。沿用五维审阅要求及第 2.1 节产物结构，按下列职责分配信息：

正文须能明确定位以下三个组件，标题可用中文或按任务组织，不机械要求固定英文标题：

| 组件 | 留在正文中的内容 | 外移并直接索引的内容 |
|---|---|---|
| Instructions（指令） | 目标、输入、关键步骤与分支、工具使用规则、核验、异常及权限边界。 | 冗长 API／schema、业务字典、复杂配置、详细算法及领域知识。 |
| Examples（示例） | 少量代表性的输入／输出对，展示正确行为、边界及失败反馈。 | 大量 few-shot 样例、场景变体与大型示例数据。 |
| 引用与扩展（资源索引） | 每项资源的用途、读取／执行条件、一跳相对路径及预期结果。 | 对应 `references/`、`scripts/`、`templates/`、`assets/` 中的实际内容；按第 2.4 节分工。 |

将正文设计为“高层任务方法 + 关键规则 + 按需索引”：主体不装入整套领域知识或完整代码，细节通过直接入口取得；授权、决定下一步的关键判断和完成标准仍留在正文可见位置。

| 披露层 | 应写入的内容 | 进入下一层的条件 |
|---|---|---|
| 识别与选择 | `name`、`description` 及适用的宿主元数据，说明用途、触发与消歧。 | 请求匹配且满足前提，或用户显式选用；显式选用仍检查能力与授权边界。 |
| 正文指导 | 目标、必需输入、关键步骤与分支、核验、失败处理、简短示例及资源读取条件。 | 当前步骤确需某领域规则、参数契约、模板或脚本时，直接定位对应资源。 |
| 按需资源与执行 | `references/` 中按域拆分的知识、`templates/` 模板和 `assets/` 素材、`scripts/` 已验证入口。 | 读取任务相关部分或执行适用脚本，再依据结果决定继续、纠正或停止。 |

- **任务与输入**：开头简要声明目标、完成标准、适用前提和所需输入；缺失时说明应澄清、按已声明默认值处理还是停止。关键能力、权限、费用或不可逆副作用在操作前可见，不藏在可能永远不会加载的附件中。
- **步骤与决策**：用明确动作写必要顺序和分支，说明每步依赖、产物与核验。对易混淆处直接作出规则或引用权威契约；对任务需要的判断保留合理执行空间，不以冗长固定脚本代替所有推理。关键检查及状态约束按第 3–4 节用实际机制落实。
- **资源入口**：在使用该资源的步骤给出“何时读／执行、直接相对路径、用于何种判断或产物”。例如需要财务口径时直接读取 `references/finance-rules.md`，销售规则则由另一个触发条件指向 `references/sales-rules.md`；这些是路径写法示意，实际 Skill 只能引用真实随包文件。不要求启动时读取全部目录，不借辅助文档继续串联其他必需知识。
- **示例与输出**：保留少量能展示关键行为的输入／输出、反例及失败反馈，说明输出格式、质量要求与验证办法。大量样例和细分规则移入对应功能域文档或模板；本次任务不涉及的领域不预载。声明部分成功、信息不足及未验证项，不用模板格式正确冒充业务正确。
- **失败与收尾**：区分可纠正输入、缺能力、权限拒绝、执行失败与结果不明，给出可行动的反馈及停止／重试条件；不能以“自行解决”代替异常分支。必要时记录状态、归档证据并清理本次临时资源，按第 4–5 节保留幂等和用户数据边界。
- **上下文经济性**：默认模型具备通用基础知识，删去基础概念复述、历史叙事及重复规则，将篇幅用于它缺少的领域方法、真实工具用法和易错判断。领域资料拆分后仍须写清读取条件；不能以缩短正文为由省略授权、关键决策或验收。按下述工程预算及目标 Host／模型检查实际加载与输出规模；脚本调用、必要审查及返回结果也可能消耗上下文，不承诺“零 token”。

**长度与预算审查**：本项目以 Markdown 正文 **不超过 500 行**为默认审查上限，统计结束 frontmatter 后的实际文本行，包含空行、表格及代码块，不通过压缩长行规避拆分。接近或超过上限时先移出详细规则、代码和大量示例，再按功能域提供一级资源入口；确需超出时，在现有 PR／设计记录中写明行数、必要性、拆分取舍及加载验证，由既有评审流程处理。此为工程预算，不是开放格式的通用语法限制；行数合格也不能证明行为合格。

正文以约 **5000 token 以内**为上下文复查参考，按目标模型／分词器记录估算口径；它与 500 行不是换算关系，也不是所有宿主的固定限制。若宿主有更严限制须同时满足；将本次实际读取的辅助文档、模板及脚本输出纳入加载预算，不能只报告正文很短。

### 2.4 资源职责与可执行索引

指令知识、确定性执行、样例与模板分别组织，均沿用第 2.1 节的一级子目录及复数 `references/`。下列文件名仅展示用途；实际项目按功能域命名，不为凑齐表格创建空文件，也不把 `FORMS.md`、`REFERENCE.md` 等书中示例当成宿主保留文件名。

| 资源职责 | 放置与命名示意 | 应提供的内容 |
|---|---|---|
| 指令与参考知识 | `references/form-rules.md`、`references/api-contract.md`、`references/style-guide.md` | 按需查阅的表单映射、API 参数／数据字典／错误码、风格及业务规则；本主题说明完整，避免串联加载。 |
| 确定性执行 | `scripts/validate_inputs.py`、`scripts/extract_metrics.py` | 已测试的校验、解析、转换或计算入口，说明输入、输出、依赖、失败退出及副作用。 |
| 样例 | `references/examples.md`；大样例按领域拆分 | 成对输入／输出、代表性反例和失败反馈；示例中的结论与真实能力一致，不混入私有样本。 |
| 模板 | `templates/report-template.json`、`templates/report-template.md` | 输出骨架、字段／类型及待填变量；给出填充与核验方式，动态渲染按第 3.2 节执行。 |
| 素材与 assets | `assets/logo.png`、`assets/report-font.woff2` | 渲染所需的图片、字体及其他非模板资源；核对来源、许可、引用及随包完整性。 |

- 正文的资源索引可用表格或就近步骤呈现，每项至少包括 **使用条件、直接相对路径、动作（读／执行／填充）、预期结果及核验方式**。例如“需要提交报告前校验输入 → 执行指定脚本 → 根据退出码及结构化错误决定继续或纠正”；具体项目须填真实文件、命令与断言，不能只写“详见附件”。
- 对成熟、重复且要求确定性的操作，消费 Skill 时复用已验证入口；不让 Agent 每次临时重写同类解析器／校验器。准备阶段交付脚本及依赖，运行阶段直接使用；无脚本需求的 Skill 不强制添加代码，也不以“请自行编写代码解决”掩盖缺失实现。
- **执行与阅读分工**：知识文档按需读取；已验证脚本按入口执行，依据退出码和输出契约核验结果，不为理解业务流程默认读取全部源码。必要来源／权限／代码审查按第 3–4 节执行；控制返回量，不承诺“零上下文”。
- 索引、资源内容及输出契约须来自同一交付版本，重命名和参数变化同步更新引用、模板、脚本及回归场景；避免正文和资源各维护一份独立规则。验收逐项确认文件存在、条件可判断、操作可执行和结果可核验，失败反馈能驱动纠正或明确停止。
- **公共资源交付**：跨技能复用资料／代码时维护单一源，记录来源提交、内容摘要、许可及源到产物的映射；准备／打包阶段将锁定版本的必需内容纳入各技能包，沿用一级资源目录和入口直接索引。发行副本不独立修改，不靠包外相对路径、失效链接或运行时拉取浮动版本取得必需资源；上游更新同步再生成、评审并回归消费技能，在独立安装包中核验版本与完整性。

### 2.5 可控性设计

对结构化、多步骤及有副作用的任务，将流程写成可观察、可核验且能停止的执行约定。`SKILL.md` 保留关键步骤和关卡，详细检查规则／契约按第 2.1 节一跳引用；需强制执行的条件用脚本、工作流、权限机制或服务端检查落实，不能仅靠模型勾选清单。探索环节保留合理试错空间，约束程度与任务风险、依赖和完成条件匹配。

#### 2.5.1 步骤化工作流与检查点

- 多步骤执行前给出简明步骤清单或状态图，明确依赖顺序、条件分支、关键关卡与完成标准；执行中随实际结果更新进度。沿用现有任务系统，区分待执行、进行中、待核验、完成、失败和不适用；不能把“已生成计划”或“命令已发出”标成“结果已核验”。简单单步任务无需为此创建额外流程文件。
- 分支条件须可判定；会改变行为的阈值、超时和重试配置记录依据、单位及有效范围。明确边界等号归属、条件重叠时的优先级，以及未知／未覆盖输入的停止或已声明降级；不以“较大”“适当”等无判据措辞代替规则，不照搬示例常量。
- 每个检查点至少说明以下内容；不是每个普通步骤都要人工审批，但依赖的检查点未通过时不得继续后续执行：

| 检查点要素 | 必须明确的内容 |
|---|---|
| 进入条件 | 所需输入、版本／目标环境、上一步产物及适用授权。 |
| 验证动作 | 实际检查命令／工具、输入范围与需核对的断言；不能只写“检查无误”。 |
| 放行证据 | 退出状态、解析结果、业务断言或外部状态，说明什么才算通过。 |
| 失败路径 | 停止受影响分支、保存必要状态和证据，按授权纠正／恢复或报告阻塞；不得静默跳过。 |

- 对删除、批量修改、外发、生产写入或扣费等操作，采用“预检 → 展示影响范围与验证结果 → 核对有效授权／必要确认 → 执行 → 核验”的关卡。确认绑定实际对象、范围及版本；缺少授权、平台要求确认或范围变化时，先准备可审阅结果再请求确认。既有授权明确且仍有效时继续执行，不机械重复索取确认；不得以笼统计划扩大操作范围。
- 检查后若目标内容、版本或范围变化，重新验证受影响条件；适用时用条件写入、版本标识或事务避免检查与执行之间状态漂移。中断和部分完成按第 4.3 节恢复，先核对实际状态，避免重复副作用。
- 进度记录关联可观察的检查和产物，最终列出完成、失败、跳过／不适用及未验证项。不能用对话中的勾选、进程仍在或返回“success”文本替代检查点证据。

#### 2.5.2 输出格式与语义契约

- 在设计阶段选择实际消费者需要的 JSON、表格或文档模板，定义字段／列／章节、类型、必填与可选、枚举、单位、日期／时区、顺序及缺失值语义。区分未知、无数据、不适用、失败和零值；不得为填满模板编造数据。
- 机器消费 JSON 时要求严格可解析的 JSON，明确是否允许额外字段、空值和部分结果；按契约用实际解析器及适用 JSON Schema／等效校验。代码围栏、注释、尾逗号和解释文字不混入纯 JSON 载荷；诊断与载荷按消费接口约定分开，本地脚本的通道与退出约定见[脚本调用契约](#31-脚本调用契约)。非 JSON 项目使用对应格式的检查，不强制引入无关依赖。
- 表格固定必要列、单元格类型／单位、空值与转义规则；文档模板固定必需章节、证据位置及输出边界。模板放 `templates/`，详细字段与校验规则放 `references/`；正文保留格式选择、使用条件、直接路径和验收入口，不复制多套独立契约。
- 输出交付前分别验证语法／结构与业务语义，包括跨字段一致性、来源对应、计算结果及关键约束。结构合格不能替代事实正确；部分成功、校验失败及未验证状态按真实契约表达，不伪装为完整成功。协议／工具已有返回格式时保持其要求，不擅自套用另一层统一封装。

#### 2.5.3 防幻觉、失败反馈与有界纠正

- 事实性结论关联可核查来源、版本／时间范围和必要定位；区分原始事实、计算结果、推断与建议。证据缺失、冲突或无法访问时说明缺口，按需要澄清或停止相关结论；不得编造文件、引用、工具结果、字段值或执行记录。
- 可确定计算、解析和校验的环节使用已验证代码或可靠工具，例如数值计算、JSON／YAML 解析和 schema 检查；不以模型的心算或“看起来正确”代替执行结果。模型负责选择方法和解释结果，业务判断仍按需求及量规核验；无代码需求的任务不强加脚本。
- 为失败提供可行动、脱敏且适合消费接口的反馈：错误类别、位置／字段、违反的条件、受影响范围、必要修正建议及是否可重试；有副作用时附已知操作状态。脚本失败返回非零退出码，工具／协议失败使用其实际错误机制；不只抛出含混异常，也不打印秘密或私有原始数据。
- 采用“生成／执行 → 实际验证 → 依据诊断修正 → 重验”的闭环，预先按任务设定自动修正的轮数、时间或成本上限。只纠正已获授权且原因明确的部分；缺授权、缺必需输入、同因反复失败或预算用尽时停止并报告，不靠无限重试或盲目重放写入获取一次成功。
- 修正后重跑受影响检查及必要回归，保留失败与最终结果的关联证据；不能删改失败用例、降低断言、改写需求或仅挑选成功输出。格式校验通过、覆盖率上升、替身测试和真实业务成功分别报告，不照搬书中案例数字作为统一质量门槛。

## 3. 脚本、依赖与执行

- 只有任务需要确定性计算或外部执行时才添加脚本；纯指令 Skill 不强加运行时、依赖清单或构建。已有可靠工具优先复用。
- 按所用语言声明运行时、包管理器、直接依赖和锁。Python 可采用 uv 与独立 `.venv`，Node.js 使用项目包管理器及独立依赖；保留已有选型，以冻结锁文件的等效方式安装，不删除锁或借用全局包修复失败。
- 环境准备与日常调用分开。准备时安装锁定依赖、完成必要构建；受限网络／离线环境预先备齐经校验的依赖包、系统工具或运行镜像，不依赖临时访问公网。日常调用复用已验证环境，不临时下载、安装、构建或升级。变更依赖时同步声明、锁及实际检查，不把自动生成脚本里的安装步骤当成默认工作流。
- 有依赖的 Skill 在 `SKILL.md` 声明必需运行条件及预检入口，详细安装说明直接按需引用。调用前检查运行时、包版本和必需系统工具；不满足时转回环境准备流程，失败边界按第 4.1 节执行。安装失败先区分版本／平台不兼容与网络／源访问受限，同因未解决不重复安装或擅自切源。
- 验证输入及路径，不把外部文本拼成 Shell、SQL 或可求值代码；调用外部程序优先使用固定可执行文件和参数列表，按目标程序语义处理选项边界，不能仅靠转义防止参数注入。调用参数与返回行为按第 3.1 节约定。
- 先审查脚本来源与副作用，再执行；陌生脚本的 `--help` 也是代码执行。解释器启动与直接执行分别说明权限和平台要求，不能统一要求所有环境执行 `chmod`。

### 3.1 脚本调用契约

- **参数与调用**：逐项定义名称、必填／可选、类型、单位、范围／枚举、默认值、缺失／空值语义及互斥／依赖关系；未知参数的处理明确约定。执行端用解析器和业务校验在产生副作用前拒绝非法输入，不能仅靠模型遵守自然语言类型要求。`SKILL.md` 提供实际入口、工作目录、适用 Shell 的调用模板、编码与超时；详细参数直接索引随包契约，不猜测参数或擅加选项。
- **结果与诊断**：CLI 明确结果、日志及文件产物各走哪个通道。约定单个 JSON 结果时，`stdout` 只输出一个完整载荷，诊断写 `stderr`；流式结果另定义分帧契约，不混用。文件产物返回可定位引用及必要完整性信息，按声明路径核验，不把 `stdout` 当成唯一取数途径；非 JSON 接口沿用实际格式。
- **失败与退出**：定义退出码与成功、参数错误、业务失败、异常、超时／取消的对应关系，以及各状态的载荷、诊断和部分产物。可控失败报告原因、受影响对象、已知副作用和修正建议，并返回非零退出码；参数解析错误也须符合约定。进程被终止可能无法返回完整载荷，调用方不得把空／截断输出或单一状态字段当作成功；部分成功与未完成状态如实表达，恢复按第 4.3 节执行。
- **等待与长任务**：自动调用入口不得等待终端问答或密码，必需输入事前准备；明确支持交互协议的入口另行验收。网络、子进程及锁等待设置与整体预算一致的时限。超时先按第 4.3 节核对进程及远端操作状态，不盲目重放；长任务按平台真实能力拆分为启动、凭任务标识查询、获取结果及取消，不以后台启动成功代替完成。

### 3.2 混合开发与动态模板

适用于任务确需代码执行的 Skill；纯指令任务不强加脚本、数据库或模板引擎。沿用第 2.4 节资源分工及第 3.1 节调用契约，不在运行时临时重写已有实现。

- **职责与闭环**：`SKILL.md` 说明何时调用、输入来源、执行顺序、结果分支和验收；Agent 通过实际可用工具执行脚本。计算、查询、转换及渲染由已验证实现完成，再解析并核验返回结果，供后续步骤或用户说明使用。模型解读须保持数值、单位、来源及时间口径，不凭空补出币种、同比／环比等业务含义；说明或展示格式按实际消费者选择。
- **输入映射**：逐项说明用户请求／上一步结果如何映射到实际参数及变量，区分原始值、规范化值和已声明默认值。相对日期明确基准日期及时区，数值明确单位与精度，枚举使用真实映射；歧义按既有缺失输入规则处理，不猜对象 ID 或静默改写意图。执行端仍按契约校验，模型规范化不能代替验证。
- **动态渲染**：模板放 `templates/`，素材放 `assets/`，渲染实现按需放 `scripts/`，变量契约及详细规则放 `references/`，由入口直接索引。定义变量来源、必需／默认／空值、格式化、条件块与缺项行为；可信模板与外部数据分开，按目标格式转义，不将输入当模板源码、表达式或命令执行。使用已验证的渲染入口并保留源模板，模型仅填充允许生成的内容，不借改写模板或脚本绕过失败。
- **产物核验**：渲染前核对数据与必需素材，输出位置及覆盖／恢复按第 4.3 节控制。渲染后核对目标文件实际存在、格式可解析／可打开、必需字段、素材及适用版式，并检查遗漏或未替换变量；内容中的数值与结论须对应已验证数据。仅退出码为零、文件存在或渲染进程完成不能证明交付合格；核验后交付真实产物引用，明确未验证项。

## 4. 工具、权限与数据

### 4.1 能力依赖与宿主适配

使用 MCP、宿主工具或脚本时，按实际依赖维护下列信息；它们是工程记录，可放在正文或按需引用的适配资料中，不是统一要求新增的 frontmatter 字段。无外部依赖的纯指令 Skill 标为不适用。

| 项目 | 要求 |
|---|---|
| 能力与标识 | 声明用途、必需／可选、所属服务及目标 Host 实际提供的名称／ID；消除同名工具歧义，不假定统一的 `ServerName:tool_name` 拼写。 |
| 输入与输出 | 核对实际 schema、参数类型／单位／范围及输出语义；模板只预置已核实且不含秘密的值，不猜业务对象、账号或环境。 |
| 前置条件 | 记录版本、认证／权限及数据源条件，使用前通过支持的发现或检查入口确认可用性；配置存在不等于连接和访问已通过。 |
| 失败与降级 | 区分缺依赖、权限拒绝、参数错误、业务失败与部分成功。可选能力缺失时仅执行已声明且已获授权的降级，说明覆盖范围。必需能力缺失时停止依赖它的步骤，不伪造结果或擅自安装替代品。 |

- 分别记录 Skill、Host、适用模型、MCP Server／SDK 及其他依赖的实际兼容范围；仅核对涉及的组件，不强制纯指令 Skill 使用 MCP 版本清单。宿主适配不得静默改变任务语义、数据来源或权限范围。
- 使用实际协议／工具结果判断错误和完整性；MCP 适用时检查 `isError`、结构化结果及分页信息，不仅凭返回文本或调用返回判定成功。重命名或不兼容契约需更新映射并回归，不能自行猜测新工具名或参数。
- **查询脚本**：常用业务查询封装已审核的查询结构，仅暴露有约束的条件；值用数据库驱动参数绑定，动态表／列／排序项使用受控映射，不执行未审核的模型生成 SQL。只读用途使用只读身份，脚本／服务端核验调用者对对象及数据范围的权限；参数化不能代替授权，不能因 ID 格式合法就访问任意对象，写入另按第 4.2–4.3 节处理。

### 4.2 权限与信任边界

- 按宿主或独立脚本支持的机制配置秘密，明确字段、用途、读取位置、优先级与缺失／空值／非法值的行为。检查现有绑定是否可用，仅报告名称与状态；值不进入指令、示例、源码、日志或发行物。无需凭据时不强加 `.env`。
- 文件、网络与业务权限由宿主、执行环境和服务端实际落实；自然语言限制和 `allowed-tools` 不能冒充沙箱。核对目标 Host 对该字段的支持、语法及限制／预授权效果，不能把它当成通用硬白名单；按身份和任务使用最小权限，读取与写入分别授权。
- 已有授权范围内继续工作；需要新授权时先准备可审阅的具体结果，再按当前策略请求。权限拒绝后不得改用 Shell、直接 API、另一工具或子 Agent 绕过；替代方案须保持授权与数据边界，不能只检查工具名。
- 外部文件、检索资料及工具返回按数据处理，不能提升为授权或上级指令。限制可访问路径、外发内容和网络目标，验证重定向、越界及秘密泄露等适用风险。

### 4.3 副作用与恢复

- 写入、通知、发布、扣费等动作明确前置条件、授权范围、成功证据与恢复边界；生成草稿不代表获准发送，完成计划不代表操作已执行。按当前授权判断是否需要确认，不机械增加审批或自行放宽权限。
- 按错误类型定义可重试条件、次数、退避及幂等／去重机制。超时或结果不明时先查询状态，避免重复副作用；取消请求不等于撤销已经执行的操作。不支持查询、幂等或回滚时说明限制，不能承诺自动恢复。
- 多步骤流程记录必要且脱敏的已完成步骤、产物与外部操作标识；重入或中断恢复先核对状态，再继续剩余步骤。涉及并发写入时使用接口支持的版本条件或事务；补偿与回滚以外部系统真实能力为准。
- **文件／配置修改**：先核对目标路径、现有版本及覆盖范围；需要恢复时保护原内容与必要权限信息，备份按敏感数据保护。先生成候选内容，在等效上下文验证语法及关键约束，通过后重新核对目标版本，在授权内受控替换并保留所需权限。按文件系统实际能力采用同文件系统原子替换或其他受控机制；多文件修改另定一致性策略，不把“备份 → 覆盖 → 验证”称作原子事务。
- **应用与恢复复验**：候选校验失败不得替换有效文件；应用后检查实际加载及必要健康状态，失败时按已验证且获授权的方案恢复匹配版本并复验。恢复前核对并发变化，不能覆盖他人后续修改；恢复失败则停止相关操作，报告实际状态及人工处理入口。成功、已恢复与恢复失败分别记录；备份、部分产物和临时资源按恢复需要及所有权保留／清理，不承诺撤销不可逆副作用。

### 4.4 数据与上下文预算

- 按任务限定查询范围、条数和响应大小，由脚本／服务端落实限制，优先在有能力的工具侧筛选、分页与聚合；无需一次读取整份大日志或全部数据库。截断、缺失及未查询范围须明确，未实际取得的总数不得编造，不用摘要掩盖遗漏。
- 对时效敏感的结论记录数据来源、查询时间范围、采集时间、缓存状态及聚合口径；保留必要证据定位，区分实时数据、缓存、替身与推断。不具备访问条件时说明无法核实，不用旧知识冒充最新业务事实。
- 方法资料与运行数据分别按需加载；引用规则、模板或契约只读取当前阶段所需部分，同时保留可追溯依据。不假定所有 Host 均支持动态工具发现、相同资源加载或统一上下文预算机制。
- **知识检索**：有稳定键的资料优先精确查找；长文按需返回命中位置及足以解释规则的上下文，确需语义检索时接入已核实的 RAG／等效能力，不强制引入外部服务。结果保留来源、版本及片段定位；未命中与调用失败分别反馈，检索分数不能证明事实正确，不凭空补全规则或将局部命中当作全文覆盖。

### 4.5 安全审核与数据出界

沿用第 4.2–4.3 节授权与恢复边界，按实际操作建立“执行前检查 → 执行 → 输出检查 → 放行／阻断并留证”的流程；只读和纯指令任务采用适用部分。Skill 文本不能自行提升指令优先级，声明红线须由实际控制与测试支撑。

- **执行前检查**：核对操作、身份、目标对象／路径／网络地址及数据范围；路径验证考虑规范化、越界和符号链接等适用逃逸。按实际结构解析参数及查询，关键词／正则拦截仅作补充，不能取代参数化、对象授权及运行隔离。拒绝或必需检查异常时停止受影响操作，不静默放行或换工具绕过。
- **数据出界检查**：在受信脚本／服务边界选择必要字段，按授权决定哪些内容可进入模型、外部服务、日志和交付物；不需要或不允许的原始敏感字段在返回前删除、掩码或使用受控替代标识。异常堆栈、诊断及 artifacts 同样检查；掩码／哈希不自动等于匿名化，不将事后模型自我过滤作为唯一防线。返回内容仍按契约检查结构、大小与完整性。
- **控制机制核实**：采用目标宿主实际支持的 Hooks、工具包装器或服务端检查时，核对版本、触发事件、输入载荷、匹配范围、阻断／输出处理能力及失败语义。不能只保护 Shell 而遗漏其他写入或外发入口，也不能将某个退出码、环境变量或配置字段当作跨宿主通则；不支持必需控制时报告缺口并停止依赖该控制的步骤。
- **阻断与审计**：用无真实权限的测试值验证合法请求可通过，越权／注入／泄露请求及必需检查超时／失败会在相应边界被阻断，确认实际操作未发生或未授权数据未离开边界。记录脱敏的规则、对象、决定及结果；后置检查不能撤销已发生的副作用，事件处置按已授权渠道进行，不自行外发原始轨迹或通知他人。

## 5. 分层验证与反馈

提供真实存在且能报告失败的本地检查入口，与 CI 共用。按变更影响选择相关层次，不用占位成功脚本或零用例结果证明可用。

### 5.1 分层验收与证据

| 层次 | 代表性检查 | 结论边界 |
|---|---|---|
| 规范与包结构 | frontmatter 类型及边界、产物一级资源子目录与命名、入口一跳引用、功能域拆分、相对链接、资源完整性、包清单与许可证。 | 检查针对单 Skill 包，不能将仓库结构视为违规；结构合格不能证明正确选择或任务成功。 |
| 脚本与模板 | 有效／非法／空输入、参数约束、结果／诊断通道、输出契约与退出状态、不同工作目录与适用平台、超时和部分失败。 | 无脚本项目说明不适用；替身不代表真实外部系统成功。 |
| 选择与触发 | 正例、反例、模糊请求、相邻／同名技能、显式与隐式调用。 | 显式调用成功不能替代隐式选择、漏选与误触发检查。 |
| 任务行为 | 分支、资料按需读取、结果正确性、证据引用、信息不足及失败反馈。 | 使用有判定依据的量规；不以输出看起来流畅代替合格。 |
| 工具组合（适用时） | 真实 Host 工具标识与参数映射、同名工具消歧、契约不兼容、必需／可选能力缺失及降级。 | 工具发现、调用成功与业务结果正确分别核验；不以替身结果声明实际组合可用。 |
| 权限与副作用 | 注入、越界读写、未授权外发、缺依赖、重复调用及中断恢复。 | 默认使用无真实权限的测试值和隔离环境；业务写入／收费按实际授权验证。 |
| 宿主与交付 | 真实目标版本中的发现、选用、资源访问、执行，以及干净安装、升级和回滚。 | 仅对实际验证的宿主、会话类型、平台及版本作兼容声明。 |

- 改正文或描述时重点回归选择和行为；改脚本、资源、依赖或打包时验证对应执行与交付链路。纯规范文档修改检查链接、示例及条款一致性，无需因此运行业务调用。
- 对渐进式披露分别验收：不读取正文时的元数据用途／触发／消歧是否清楚；选用后正文能否指导正确执行与失败处理；领域任务是否只读取必要资源且保持一级引用。覆盖自然语言正例、近邻反例、模糊请求及缺前提场景，记录实际读取路径和结果；没有轨迹或可观察证据时不声称已验证加载范围，格式合格也不能证明正确触发。
- 写作审查记录解析后 `name`／`description` 的字符数、正文行数及适用的 token 估算；核对 Instructions、Examples、资源索引三个组件和第 2.4 节资源分工。检查超预算是否已拆分或记录必要例外，并验证索引的条件、路径、动作与预期结果一致；长度、结构和行为分别报告，不将三者互相替代。
- 对第 2.5 节覆盖正常放行、关卡失败后的停止、授权缺失／范围变化、中断恢复、非法或缺字段输出、结构正确但语义错误、证据缺失、可纠正失败及修正预算耗尽；根据实际任务选择适用场景。验证后续受影响步骤确实未被执行、未知数据未被编造、输出契约有效且失败不会伪装成功，不能只检查清单或模板是否存在。
- 条件分支覆盖阈值下方、恰好等于、上方及适用的未知／重叠输入，核对分支选择与停止／降级结果；用实际规则及其单位构造边界，不以仅正常路径通过证明流程完整。
- 脚本契约通过真实入口覆盖必填缺失、类型／枚举／组合非法、默认值／空值、参数解析失败、执行异常及截断结果。将调用模板、实际输出、文档样例与同一权威契约核对字段、层级、语义和退出状态；合成样例标明用途，正常样例须校验通过，错误样例标明违反的规则，防止日志污染载荷或示例与实现漂移。
- 混合型 Skill 验证“请求／前序结果 → 参数映射 → 实际执行 → 返回核验 → 解读／渲染 → 产物验收”闭环；按实际能力覆盖相对日期／单位歧义、结果口径保留、查询注入与对象越权、未命中／失败及截断，确认不会绕过脚本自行编造数据或在失败后宣称完成。
- 动态模板覆盖缺变量／素材、非法数据、特殊字符转义、未替换变量、渲染失败及已有输出冲突；用可核验数据检查最终产物的内容、格式及适用版式，确认源模板与用户文件保持约定状态。模板、变量契约、脚本或素材变化时回归对应渲染链路。
- 文件／配置修改在隔离环境覆盖候选校验失败、应用／健康检查失败、恢复失败及适用的并发冲突，核对有效原内容未被误替换、实际恢复结果和诊断；同时检查权限及用户文件的保留行为，不以有备份证明已恢复。
- 工具型 Skill 验证权限拒绝和恶意工具返回不会诱导绕过边界，并覆盖超时后状态不明、重复调用、取消与部分完成后的恢复；关键步骤检查实际产物或执行记录。用受控场景验证，不为测试取得生产写权限。
- 固定评测集、场景标识、输入来源和量规版本；模型行为按预先约定的次数重复运行，按第 5.3 节报告指标及版本差异，不挑选一次成功或硬套统一比例。
- 记录 Git／Skill／资源／依赖版本、宿主／模型／平台、命令或调用、预期与实际结果、退出状态及未覆盖项。区分通过、失败、预期失败、跳过、不适用和未运行；证据脱敏，必要的受控证据与私有原始轨迹分开存放。
- 测试前明确工作目录和临时资源范围，优先使用工作目录内独立且已忽略的临时子目录。平台或工具确需系统临时目录等外部位置时，记录本次创建的路径及清理方式；不向无关目录散落测试文件。
- 测试结束后先归档必要且已脱敏的证据，包括版本、命令、结果、退出码及必要的失败日志，关联任务并记录归档位置；本地放在工作目录内约定位置，CI 使用设定保留期限的 artifacts。证据不得含秘密或用户私有数据，归档不等于自动提交 Git 或发布。
- 证据归档后及时停止本次测试进程并清理本次创建的临时文件、环境与资源，复查外部临时路径无遗留；成功、失败或中断均通过清理钩子（如 `finally`、Shell trap 或 CI 始终执行的收尾步骤）落实。仅清理本次拥有的资源，保留用户环境、测试源码、fixtures 和归档证据；清理失败须报告遗留路径、原因及后续处理，不宣称清理完成。
- 交接提供变更范围、验证证据、未决项与接手入口。根据失败原因修正描述、方法、资源、工具或执行控制，并保留回归样例；不把所有问题都变成入口新增文字。

### 5.2 调试诊断与归因

采用“最小复现 → 对齐阶段证据 → 验证原因 → 最小修正 → 原例及反例回归”。先固定失败请求与实际版本／环境，用已授权的脱敏样例复现；诊断入口按 Codex、Claude Code、DeepSeek Harness 的实际版本选用，不统一套用某个调试开关或日志字符串。

| 阶段 | 核对证据与处理方向 |
|---|---|
| 发现 | 核对当前作用域、实际来源／版本、解析后的名称与描述及宿主可见信息；优先排除路径、格式、同名来源和刷新问题。没有读文件日志不能单独证明未发现，宿主可能通过缓存或其他机制加载。 |
| 选用 | 对照显式／隐式调用策略、目标意图与近邻反例，检查可观察的选择／加载事件；已发现不等于已选用。确认此请求本应使用该技能后再修改描述或边界，不为提升触发率扩大能力声明。 |
| 执行 | 核对必需步骤、工具／资源、规范化参数、输入来源、进程或操作标识、退出状态与返回通道。纯指令任务无工具调用可属正常；需要实时数据或确定性执行的任务不得用记忆结果冒充已执行。 |
| 验收 | 检查返回内容、完整性、事实／业务断言及实际产物，区分执行失败、解析失败、解读错误和产物不合格；不能由加载成功或调用返回推断任务成功。 |

- 按时间／调用标识关联必要的脱敏事件、工具请求与结果、检查点及产物；轨迹缺失时标为未核实，不臆测根因。可观察执行记录不等于模型完整内部思考，不要求暴露内部推理或采集无关会话。
- 优先修正最早有证据的失败阶段，并重验受影响链路；格式及调用按第 2.2、3.1 节，纠正／重试与停止按第 2.5.3、4.3 节执行。错误原因不明时先诊断，不把文件缺失猜成权限不足后提权，也不因任何可恢复错误都机械停下等待指示。

### 5.3 质量评测与版本对比

- **先定判据**：为用例记录目标、输入与前提、预期选择／必需执行路径、产物断言、禁止副作用、判定方式和失败条件；覆盖正常、边界及对抗场景，同时保留合法近邻请求以检查误拒绝。开发／调参样例与保留回归／验收集区分，变更用例或阈值须说明依据，不以修改判据掩盖回退。
- **分工评分**：可确定结果用独立可信基准或校验器验证，避免测试仅重复实现逻辑；复杂业务由有相应知识的评审者按量规判断。使用模型裁判时固定其版本与量规，并用人工／确定性样本校准；裁判评价不能替代实际权限、执行状态或事实证据。

按任务选择适用指标，预先约定阈值、重复次数及统计口径；结构正确、任务成功、安全与性能分别报告，不以单一平均分替代验收。分母为零时说明无样本，必需项未运行仍属未验证，不记为零失败或全部通过：

| 指标 | 定义与报告要求 |
|---|---|
| 选择质量 | 按每次评测运行计数：应触发请求中的正确选择次数／该类运行次数，以及不应触发请求中的误触发次数／该类运行次数；显式与隐式调用分别统计，不以显式成功替代自动选择结果。 |
| 任务与过程 | 业务任务通过率为满足全部必需判据的运行数／该类实际运行数，失败、超时及部分完成保留在分母；预期拒绝／失败样例按其判据单独统计。另列计划／实际用例数、重复次数、未运行项及必需步骤判定，不只在成功样例中计算质量。 |
| 安全 | 分别记录越权／泄露／注入成功、应阻断操作实际未执行的证据及合法请求误拒绝；硬性安全红线失败独立阻止放行，成本或平均成功率不能抵消。 |
| token 与费用 | 使用宿主实际提供的用量，注明输入、输出、缓存口径及估算／实测区别；计入加载、工具返回与重试，外部执行费用按需单列。未观测部分标为未知，不宣称脚本执行零 token 或必然节省成本。 |
| 端到端时延 | 记录请求到最终响应／产物交付的实际耗时、样本量与分布（如中位数和适用分位数）；按可观察时间戳分解等待、执行和结果处理，失败／超时单列，不虚构内部推理耗时。 |

- **同条件对比**：重要变更以已验证稳定版本为基线，在隔离环境用同一版本化用例集、数据快照、宿主／模型配置与重复策略成对比较；注明依赖、权限、缓存冷热及运行环境差异。可串行使用隔离会话，不强制部署两个服务或将离线版本对比当作线上用户 A/B 实验；新增能力单独验收，无法同比的项目注明原因。
- **修复再放行**：对照既有功能、边界与安全判据及预先约定的成本／时延预算，报告逐项差异与失败样例。不可接受回退先修复并重跑受影响回归；允许的性能取舍走既有评审，未运行必需项不记为通过。失败案例回流评测集，放行证据关联实际提交与第 6 节交付记录。

## 6. CI/CD 与版本交付

全线采用分支 → PR → 必需 CI 检查与评审 → 合并后复验 → 受控 CD。GitOps 以 Git 中经审核的声明为目标状态，通过授权自动化同步并核对实际版本，不仅是将文件放入 Git。消费项目应交付实际工作流、可复现检查入口和已生效的门禁；模板条款不授予提交、推送、合并或发布权限。

### 6.1 GitOps 版本基线与审核

- **声明完整基线**：指令、引用资源、脚本、依赖声明／锁、评测及交付配置一并版本化；沿用项目清单记录目标 Skill 版本、来源提交、产物摘要、适用宿主及必要运行环境。秘密只保留受控引用，不将凭据值写入 Git。
- **隔离开发与正式使用**：实验在分支及独立技能加载位置／环境进行，不覆盖正式版本或共用可写依赖。按 Codex、Claude Code、DeepSeek Harness 的实际发现、优先级与重载行为核验有效版本，防止本地同名技能遮蔽。正式使用锁定完整 Git SHA 和产物摘要；语义化 tag 必须解析并记录对应提交，不依赖分支名、`latest` 或可移动标签，禁止原地改写已发布版本。
- **审核全部行为变化**：PR 展示入口及间接加载内容的差异、变更理由、兼容影响和验证证据；维护者重点审查触发／工作流、提示注入、数据读写与外发、权限扩大、依赖来源和副作用。新增资源及脚本同样受审，不把 Markdown 视作无风险文本；补充相关反例及失败回归，自动检查不能替代语义与权限评审。
- **代码化可验证约束**：将结构、引用、锁与秘密等确定性检查接入必需 CI；关键计算、校验和操作边界按任务落实到脚本、工作流或服务端。脚本本身也须审查和测试，不能保证防注入；依赖在准备阶段锁定安装，日常调用不动态获取或执行未审核代码，按第 3 节执行。
- **落实运行隔离**：审核实际文件、网络、凭据和工具权限；按第 4 节用目标宿主／执行环境支持的机制限制，并验证拒绝路径。不照搬 Claude 专用配置到其他宿主，不把 `allowed-tools`、提示词或允许绕过沙箱的命令列表当作隔离保证；无法落实的限制须报告，不声明已实现。
- **同步与检测漂移**：受控自动化从已审核目标拉取并校验同一已验证产物，安装／升级后核验有效版本及必要行为；按约定触发点或周期比较目标与实际提交、摘要和配置。漂移须报告并在既有授权内恢复或通过 PR 调整目标，不将现场改动静默当作正式基线；个人环境按授权更新，不擅自覆盖定制。
- **保留审计与回滚链**：关联 PR／评审、CI、完整提交、发行摘要、目标环境、同步结果及操作者／自动化身份。失败停止扩散，按预先授权的恢复策略切回已验证版本并复验，同时记录或通过 PR 恢复 Git 目标，避免自动化再次推入故障版本。紧急处置须补齐审核记录，不修改历史发行物，不承诺撤销已发生的业务副作用。

### 6.2 CI/CD 门禁与交付

| 阶段 | 要求 |
|---|---|
| PR CI | 锁定安装适用依赖，按影响运行结构／文档检查、脚本测试、选择／行为评测、必要构建、秘密扫描及适用依赖风险检查；不适用项记录依据。 |
| 默认分支 CI | 对实际合入提交复验，缓存与先前 PR 成功不替代当前结果。 |
| 发布 CD | 受控标签或批准的入口核对完整提交及必需检查，验证包内容与安装后发布真实版本、清单、摘要、变更说明和验收证据。失败停止，不覆盖已发布版本。 |
| 同步／部署 CD | 复用已验证产物，按目标环境授权安装／同步并核验，失败按已验证方案恢复；仅有服务目标时执行服务部署，不强加常驻服务、容器或集群。 |

- 在分支保护或 ruleset 中要求实际状态检查与评审；核对权限、检查名称及跳过条件。仅有工作流文件不能证明门禁生效；无法配置的限制如实报告。
- 确定性检查适合每次 PR。模型评测按变更、预算及发布风险分层，并按第 5.3 节执行基线对比和放行判据；未能自动化时保留可复现的人工评测和实际发布放行机制，明确覆盖限制，不把手工结果冒充自动检查。
- 工具映射、检查点、输出契约、模板、权限、副作用或自动纠错流程变化时，触发第 5 节相关行为、组合与失败路径回归；声明支持的 Host／Server 版本变化补兼容验证，破坏性变化给出迁移说明。不强制无外部依赖的 Skill 建立工具联调流水线。
- 最小化流水线权限，不可信 PR 不接触生产秘密或发布权限；不在高权限流程中执行不可信 PR 代码／产物。第三方 Actions 固定到已核对来源的完整 SHA；秘密经受保护机制注入，不进入缓存或 artifacts。
- 发布关联 tag、完整 Git SHA、技能与依赖版本、评测记录及校验摘要；适用时提供来源证明。发布内容按实际运行引用确定，安装与升级验收见[手册指南](MANUAL-WRITING-GUIDE.md#6-发行内容与交付验证)。

## 7. Git 跟踪与忽略规则

合并[`.gitignore` 模板](../.gitignore)时保留项目已有规则，按实际工具裁剪并验证。Git 跟踪、CI artifacts 与发行内容分别判断。

| 应跟踪 | 应忽略 |
|---|---|
| `SKILL.md`、脚本源码、引用资料、必需 assets 及许可证。 | 依赖、虚拟环境、工具缓存和可重建构建输出。 |
| 测试源码、安全 fixtures、评测场景／量规、golden 与快照。 | 测试报告、覆盖率、临时评测工作区、私有运行结果及原始轨迹。 |
| 声明与锁、CI、共享宿主／插件模板、规范和手册。 | 秘密、认证、会话、本机配置、运行数据与日志。 |

- 模板覆盖常见 Python／Node 缓存、测试／浏览器报告、基准和变异测试产物；未锚定的测试规则覆盖子项目。根 `.eval-runs/`、`.eval-cache/`、`.eval-workspaces/`、`eval-results/`、`eval-reports/`、`eval-traces/` 保留给生成状态；`evals/` 不整体忽略。
- 不用 `tests/`、`*.test.*`、`test_*.py` 或泛化的 `*.json`／`*.db`／`*.lock` 排除正式资产；共享 `.agents/skills/`、`.claude/skills/`、`agents/openai.yaml` 等按用途保留。正式 `outputs/` 与可重建 `output/` 分开处理。
- 生成物与输入样例分目录。必须跟踪的安全 fixture 若命中报告名或日志规则，审查后添加精确反向规则，并处理必要的父目录例外；不要整体放开测试目录而带回秘密或缓存。
- 修改规则后，在临时 Git 仓库应用目标模板，用 `git check-ignore -v --no-index -- <path>` 验证应忽略项与可跟踪项，并用合成文件的暂存清单核对。覆盖顶层、子项目、测试／fixtures／锁／CI／共享配置及特殊例外，不借维护仓库规则掩盖缺陷。
- 忽略规则不追溯移除已跟踪文件，也不清除历史秘密；不为应用规则删除文件或批量取消跟踪。发现泄露按凭据处置流程处理；发行包必须独立检查。
